# home-kai

Команды двух видов:

- **Эта машина** (`status`, `ping`, `agent`) — ходят в unix-сокет локального `kai-agent`, токен не нужен. Сокет `0660 root:kai`: без группы `kai` нужен sudo (отказ — `kind: auth`).
- **Сеть** (всё остальное) — admin API координатора. Настройки и источник токена — в справке ниже; что подставилось на самом деле, показывает `home-kai doctor` (токен — маской).

Агенту — `--json`: конверт в stdout, и отказ тоже, код дублируется в поле `exit`. Текст по умолчанию — для человека.

## Безопасность

- Admin-токен — секрет. В чат, логи и argv не выводить; его место — sec, в `admin.json` только ссылка `token_ref`. Если `doctor` предупреждает о токене открытым текстом — предложить перелогиниться с `--token-ref`.
- `~/.config/kai/lock.key` (ключ network lock) живёт только на админской машине: не копировать и не показывать.
- `token create` и `peer create` печатают одноразовый enroll-токен и приватный ключ static peer — это и есть результат команды, но в чат их пересказывать только по просьбе.

## Сценарии

**Новый узел (Linux/macOS).** `home-kai token create --name <имя>` — имя задать сразу: переименовать узел нельзя, только `node delete` и повторный enroll (новый id, новый IP, снова `lock sign`). На узле под root выполнить напечатанную join-команду (флаги `--advertise-routes`, `--rekey-days`, `--no-hosts`). При `require_approval = true` узел висит без доступа до `node approve <node_id>`; при включённом network lock он не заработает до `lock sign`.

**Телефон или роутер.** `home-kai peer create iphone --png iphone.png` — QR для официального клиента WireGuard, `--full` — весь трафик через хаб. Имена `*.kai` на static peer работают через DNS хаба, прописанный в конфиге.

**Subnet router.** Узел анонсирует LAN (`kai-agent up --advertise-routes 192.168.1.0/24`), в netmap подсеть попадает только после `home-kai node routes <node_id> --enable 192.168.1.0/24`.

**ACL.** Сначала теги (`node tag`, `peer tag`), потом `policy create`. Первая же включённая политика переводит сеть в режим «запрещено всё, кроме явно разрешённого»: до включения проверить, что нужные пары тегов покрыты. Enforcement на Linux-агентах и хабе (iptables `KAI-FILTER`/`KAI-FORWARD`); macOS при ACL теряет прямые p2p-пути и ходит через хаб.

**Network lock.** `lock init` создаёт ключ — сразу предложить забэкапить `~/.config/kai/lock.key`; затем `lock sign`. После нового устройства или ротации WG-ключей — снова `lock sign`. Откат — `lock disable`.

**Диагностика.** `home-kai status` — путь до каждого пира (`direct` — p2p, `relay` — через хаб), handshake, трафик; `home-kai ping <имя>` — резолв, путь и три пинга (код 1 — не ответил). Data plane живёт без координатора: он лежит — туннели работают на закэшированном netmap. Отказ сетевой команды — `home-kai doctor`: там видно, чего не хватает — настроек, токена или ответа координатора.

**Выключить оверлей на этой машине** (например, чтобы 100.87/16 шла через другой туннель) — `home-kai agent down`, вернуть — `agent up`. Обе перезапускаются через sudo; без терминала и без закэшированного sudo отказ `kind: auth` — попросить пользователя выполнить команду самому.

Оверлей по умолчанию `100.87.0.0/16`, хаб `100.87.0.1`, имена устройств `<имя>.kai`. Web UI с тем же набором действий — `https://<хаб>:8444/ui`. Подробный гайд — `docs/tutor.html` в репозитории home-kai.
